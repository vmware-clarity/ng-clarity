The contextual engine gives AI agents structured, always-current context about the page your application is showing: the active route, what is rendered right now and what state it is in — every button, link and field where it sits on the page — and whatever the application chooses to say about itself.

How it describes the page

The engine reads the accessibility tree, not any library's selectors. An ARIA role, an accessible name and ARIA state mean the same thing on a Clarity Angular component, on @clr/ui CSS-only markup, in another component library and in plain semantic HTML — so one implementation describes all of them, and nothing has to be taught about a component before it can be described.

That is why a component reports itself as its role rather than its tag: a datagrid is a grid, a modal is a dialog. Where the role is too coarse, an element field carries the tag that rendered it, so a clr-side-panel and a clr-modal remain distinguishable while both being dialogs.

Components add only what a role cannot express — a combobox's options while its popover is closed, a datagrid's total row count while paginated.

What it guarantees

Pull, never push. A snapshot is computed at the moment it is requested, from the live DOM. Nothing is cached, so a snapshot cannot describe UI that has been closed, destroyed or navigated away from.

Bounded output. Text is truncated, collections are capped, hidden elements are skipped and collection roles are summarised rather than listed, so a ten-thousand-row grid does not become ten thousand nodes.

Read-only. The engine describes the page and never changes it. Applying a value an agent proposes is a decision that needs a person to approve it, which belongs to a review surface rather than to a context engine.

Only what is relevant, configured once. Size budgets keep a snapshot small and relevance options keep it useful: whole landmarks, selectors or nesting levels can be left out, an open modal can be all that is described, and collections can be reduced to counts and selection — set once for the whole application, with per-call overrides, and with a stream of what changed for conversations.

Sensitive values never leave. Passwords, file inputs and anything whose autocomplete declares a credential or a payment card are reported as redacted rather than by value, as is anything marked data-clr-context-redact. Embedded frames and the browser-agent accessor receive no form values at all unless the application deliberately shares them.

Who consumes it

An assistant inside your application injects the service and asks for a snapshot per question, or subscribes to the tracker to always hold the current page. An assistant embedded in an iframe — possibly built with a different stack entirely — pulls context over a framework-agnostic postMessage protocol. An agent driving the browser from outside reads window.clrContext(). Each of those is a different trust boundary, and each is configured separately.

Keeping a live page context

Consumers that always want the context of the page the user is currently on subscribe to ClrContextTrackerService. It watches the DOM with a MutationObserver created outside the Angular zone, and watches input and change too, because typing changes a property rather than an attribute and is invisible to an observer. Both feed one quiet window of debounceMs (default 300), bounded by maxWaitMs (default 2000), so a burst of activity results in a single scrape and an emission happens only when the context actually changed.

Mark UI that renders the context with data-clr-context-ignore. Such regions are invisible to the engine end to end, so a panel re-rendering the context cannot re-trigger tracking or describe itself into the page context.

Annotating the application

The DOM only knows what is on the page. The clrContext directive lets the application add the why — knowledge only it has. Annotations register when the element appears, unregister when it is destroyed, and are read at snapshot time, so they are never stale.

Reading form context

A field is described by what it is, what it permits and what it currently holds: its label and type, the options it offers, its min, max, step, pattern and maxLength, its validation state, and the helper or error text that describes it — resolved from aria-describedby, so it is attached to the field it belongs to rather than floating beside it.

State the DOM cannot show

Some state lives only inside component instances — a combobox's options render in a popover, yet the component always knows them. Any component can publish that truth with publishElementContext from @clr/angular/utils. The collector calls it while scraping and merges the result over what the DOM showed. ClrCombobox ships this built in, and so does ClrDatagrid for its total row count while paginated.

Markup that carries no semantics

Well-formed markup needs no help: anything with an ARIA role, an accessible name or a custom element tag is described automatically, whatever library rendered it. What the engine cannot describe is markup that says nothing about itself — a bare <div class="card">. Register an extractor for those; the returned function removes it again.

Serving context to embedded frames

UI embedded in an iframe — such as a chat assistant built with a separate UI library — can receive the hosting page's context. An embedded document is trusted less than the application that embeds it: same-origin only by default, no form values, no URL query string, and one snapshot per frame per minRequestIntervalMs so a frame in a loop cannot keep the host's main thread busy.

The protocol is two plain JSON messages over postMessage (see CLR_CONTEXT_PROTOCOL), so the embedded page needs neither Angular nor Clarity. Requests are answered per frame and per request with a freshly computed snapshot, addressed to the origin that asked — context is never broadcast.

A hand-written implementation gets none of the protections requestHostContext() applies, so reproduce two of them: accept a response only when event.source === parent, and use an unguessable requestId. Sibling frames can reach each other through parent.frames, so a listener that matches on the id alone can be answered by any frame on the page.

Browser-driving agents

Agents that drive the browser directly and have no application API can be given a global accessor. Any script on the page can call it, so what the user typed is withheld unless the application shares it deliberately.

Keeping snapshots lean

Everything in a snapshot is bounded, and every budget can be tuned per call. Note that maxComponents stops the walk when it is reached, so a low value drops whatever comes last in the document rather than sampling evenly — and the snapshot then carries truncated: true.

Choosing what to collect

Size budgets keep a snapshot small; relevance options keep it useful — the difference between a page described in 300 nodes and the 40 that matter to the question being asked. An assistant does not need the sixty links of the navigation in every snapshot, nor the page behind an open dialog. excludeCategories leaves out whole kinds of content by name — layout (header, navigation, footer, side panels), actions (buttons, links, menus), forms, headings, collections, dialogs, status, images, text, frames — and excludeRoles does the same for a single ARIA role; excludeSelectors and rootSelector do it by CSS selector, maxDepth caps nesting, focus: 'modal' describes only the open modal while one is open, and collectionItems: 'summary' reduces lists, options and tabs to counts and the current selection.

Set them once for the whole application rather than at every call site. Three presets bundle the common choices: full (the defaults), interactive (no prose, no layout) and minimal (no prose or layout, summary collections, shorter text, a lower budget, modal focus). Per-call options are applied over the application's.

Sending only what changed

In a conversation the page is described once; after that, what a model needs is the difference. ClrContextTrackerService.changes$ emits alongside every context$ emission: nodes added (with their subtrees), removed, and changed in their own state, plus whether the route, title or annotations moved. The first emission after start() lists everything as added. diffClrContext() is the same comparison as a plain function.
