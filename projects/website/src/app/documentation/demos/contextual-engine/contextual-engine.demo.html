The contextual engine describes the page your user is looking at, so an AI assistant can answer questions about it. One call returns the route, the controls on the page with their labels and state, and a summary of each table.

When to use it

  • An assistant answers questions about the current page, such as "why can't I save this form?".
  • An assistant guides the user through a form or a workflow they have open.
  • An assistant summarises what is on screen.

It describes what is rendered. To give a model your records in bulk, use your own API.

How it works

  • It reads the accessibility tree: roles, accessible names and ARIA state. That works the same for Clarity components, @clr/ui markup, other libraries and plain HTML. A datagrid is reported as a grid, a modal as a dialog.
  • Roles follow HTML-AAM and names follow Accessible Name Computation 1.2, as a screen reader gets them. State keys are the ARIA attribute names without aria-, such as readonly and haspopup. The element with focus has focused: true.
  • A <form> or <section> without a name has no role, so its fields are reported as part of the page. Give a form an aria-label to keep it as one node.
  • A component can add state the DOM does not show, such as a combobox's options while it is closed. The combobox, datagrid, wizard, stepper panel, timeline step, tree node, alert, file input and datepicker do this built in; the API tab lists what each publishes. Your own components can too, see Publish a component's state.
  • It walks into open shadow roots, so a web component is described by what it renders, with slotted content where its slots place it.
  • Each snapshot is read from the live page when you ask for it. Nothing is cached.
  • Reading never changes the page. Writing back is a separate service, see Fill forms and navigate.

What a snapshot leaves out

  • Hidden elements.
  • Table cells as nodes of their own. A table or datagrid is reported by its columns, its rows (one line each), row count and selection, plus the form controls in its cells.
  • Text past 100 characters, and elements past the first 25,000. A cut snapshot has truncated: true.
  • What is not rendered, such as rows a virtual scroller has not drawn, or a chart drawn on a canvas. Add those with an annotation.
  • Closed shadow roots and cross-origin frames. Open shadow roots and same-origin frames are read.
  • Hidden text that aria-labelledby or aria-describedby points at. No user sees it, so it could carry instructions meant for the model.

Privacy

Your own code gets the page as the user sees it, including the values in its fields. Only passwords, file inputs and fields whose autocomplete names a credential or a payment card are withheld automatically. Before a snapshot goes to a model:

  • Mark fields the model must not see with clrContextRedact. They are still described, without their values.
  • Mark parts the model does not need with clrContextIgnore.
  • Treat the snapshot as you treat the page's data: it can hold names, addresses and other personal data.
  • Keep ClrMutationService results in your own code. They carry the values a write replaced, with nothing withheld.

Code & Examples

These steps add page context to an assistant. Steps 1 and 2 are all a working assistant needs. The rest make it safer and cheaper.

Install

The engine is the @clr/angular/ai entry point of @clr/angular. If your application already uses Clarity, there is nothing to install.

Step 2: Send it to your model

Post the question and the snapshot to your backend. There, put the snapshot in the prompt as data, apart from your instructions.

The snapshot holds whatever text the page shows, including text your users wrote. If a comment says "ignore your instructions", the model reads that too. Delimiting the snapshot and saying it holds no instructions keeps the model from following such text.

Step 3: Leave the assistant out

The assistant's panel is on the page too. Mark it with clrContextIgnore, so the snapshot does not describe the conversation back to the model. Both clrContextIgnore and clrContextRedact are directives: import ClrContextIgnore and ClrContextRedact, or ClrContextModule. The marks are kept off the DOM, so page content cannot plant one to hide itself.

Step 4: Hide sensitive values

Mark a field or a region with clrContextRedact. The model still learns that the field is there, but not what it holds.

Step 5: Send less

A whole page can cost thousands of tokens. Choose a preset once, when the application starts:

Preset What it sends
full Everything. This is the default.
interactive No prose, and no header, navigation or footer.
minimal What interactive sends, and only the open modal while one is open.

One call can ask for less again. Its exclusions add to the configured ones, and its other options replace them:

A snapshot describes everything that is rendered, so a long list or grid is sent whole. To send less, narrow root or lower depth. The API tab lists every option.

Step 6: Add what only your application knows

The page shows what is there, not why. Bind [clrContext] on an element to tell the model what a section is for. Its label and state are added to that element's node.

A function is called on each snapshot, so its state is never stale. Keep it small, since it goes into every snapshot. The directive needs a binding: static text such as clrContext="..." would be readable by every script on the page, so it is a type error. With NgModules, import ClrContextModule instead of ClrContext.

Describe the view

On the view root, the element root selects, or an element around it, the annotation describes the whole view: its state becomes the snapshot's metadata.

With configure({{ '{' }} views: 'enabled' {{ '}' }}), only views with an annotation on their root are read. Any other view is reported as enabled: false, with nothing about the page.

Step 7: Send only what changed

In a conversation, send the whole page on the first turn and only the difference after that. clrDiffContext() compares two snapshots.

Other ways to add context

[clrContext] covers most needs. Use one of these when it does not fit:

When Use
The knowledge lives in a service, such as the user's role, or has to be fetched A ClrContextProvider registered with ClrContextRegistryService, reported in regions. It may answer with a promise.
A component of yours holds state its markup does not show ClrContextService.publish()
Markup you cannot change has no role or name An extractor

Publish a component's state

Publish from the component's constructor. The function is called on each snapshot, and what it returns is merged over what the DOM shows.

A filtering list shows what the user typed through the options it keeps. In a combobox of your own, mark its popover clrContextIgnore, as clr-combobox does, and publish the options as matchingOptions, so the snapshot says they are matches.

Describe markup without semantics

An extractor's result replaces the element's node, and the engine does not read inside the element. Return the children you want kept.

Fill forms and navigate

ClrMutationService lets the assistant act on what it read: it fills form controls that have an Angular form binding, and navigates through the router. It never submits or clicks. The user does that.

Step 1: Decide what the assistant may change

Nothing is writable until you provide a policy. It classifies each operation as reversible, consequential (applied only after confirm agrees) or forbidden. Start from an allowlist:

Never classify everything as reversible. Anyone who can put text on the page could then have the model fill any bound field.

Step 2: Have the model name controls by ref

With a policy in place, each writable control in the snapshot has a ref. Tell the model to name a control by its ref and to copy its label into description.

  • A ref stays the same for an element from one snapshot to the next, and cannot be guessed.
  • A ref whose element has left the page is refused as stale, never redirected.
  • A description that misses a word of the label is refused as mismatch, so a ref that drifted onto another field is caught.

Step 3: Apply what the model asks

Values are what the model would say: an option's label, true for a checkbox, a number, a date string, the rows to select in a datagrid. A value is written as user input arrives, so validation messages show. Each result says what the control holds now, whether it is valid, and the value it replaced:

Give the results back to the model, with the report's fresh snapshot, so it can fix what was refused.

Step 4: Navigate

A navigate operation takes a route pattern from availableRoutes and values for its parameters. It goes through the router, so your guards run, and the result says where the page ended up.

The model chooses the query parameters, so the policy has to judge them, as the example in Step 1 does.

What it will not do

  • Submit, click, or run your (change) and (blur) handlers. valueChanges and ngModelChange do fire.
  • Write a control that is hidden, disabled, read-only, ignored or redacted, or one behind an open modal. A field moved off-screen is still offered, so keep such fields out of the policy.
  • Write a control that has no Angular form binding.
  • Write for a caller you do not control, such as an embedded frame. Those get snapshots without refs.

ClrCombobox, ClrDateInput and datagrid row selection are writable as they are. A control of your own is writable when it renders a textbox, checkbox, switch, spinbutton, slider or radio group and its model holds what it shows. Publish its value as state.value so results can report it.
